# craftcms-docker

Shared base image for Craft CMS projects deployed with [Coolify](https://coolify.io) (or any Docker host).
Built on [serversideup/php](https://serversideup.net/open-source/docker-php/) and rebuilt weekly to pick up upstream security updates.

PHP extensions, the MySQL client and Composer live in the image, so a project deploy only installs
dependencies and copies code instead of compiling extensions every time.

## Image

```
ghcr.io/samuelreichor/craftcms-docker:<php>
```

`<php>` is `8.3`, `8.4` or `8.5`, for `linux/amd64` and `linux/arm64`. Every build is also tagged with its
date (e.g. `8.4-20261102`), so a project can pin a specific build.

What's inside:

- nginx + php-fpm, webroot `/app/web`, opcache enabled
- PHP extensions `bcmath`, `gd`, `intl`, `imagick` on top of the serversideup defaults (`pdo_mysql`, `zip`, `opcache`, …)
- Composer, `git`, `unzip`, `bash`, `vim`
- MariaDB client as `mysql`/`mysqldump`, wrapped to skip TLS verification of MySQL's self-signed certificate, so `craft db/backup` works
- Craft's writable paths (`storage`, `web/cpresources`, `web/assets`, `.env`) owned by `www-data`, everything else is read-only for PHP
- `X-Powered-By` removed, security headers (HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy) from serversideup
- `TRUSTED_PROXY=local`, so nginx and Craft see real visitor IPs behind Coolify's Traefik (set `TRUSTED_PROXY=cloudflare` when Cloudflare proxies the site)

The same image runs the queue worker: any command other than the default skips nginx and php-fpm
(`command: ["php", "craft", "queue/listen", "--verbose"]`).

## Usage in a project

Copy one of the examples into the project root:

- [`examples/craft`](examples/craft): classic Craft site (Twig + Vite assets) with `web`, `queue` and `db`
- [`examples/craft-no-node`](examples/craft-no-node): Craft without a frontend build step (headless/API-only or Twig without Vite)
- [`examples/craft-nuxt`](examples/craft-nuxt): headless Craft + Nuxt SSR on one domain
  (create the `NUXT_*` variables in Coolify's Environment Variables, Coolify passes them to the build)

The project Dockerfile is short:

```dockerfile
ARG PHP_VERSION=8.4
ARG NODE_VERSION=22

FROM node:${NODE_VERSION}-alpine AS assets
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM ghcr.io/samuelreichor/craftcms-docker:${PHP_VERSION}
COPY .coolify/nginx/ /etc/nginx/server-opts.d/
USER root
COPY composer.json composer.lock ./
RUN composer install --no-interaction --no-dev --no-scripts --no-autoloader
COPY . .
COPY --from=assets /app/web/dist ./web/dist
RUN composer dump-autoload --no-dev --optimize \
  && chown -R www-data:www-data storage web/cpresources web/assets .env
USER www-data
```

## Security

The setup follows Craft's [Securing Craft](https://craftcms.com/knowledge-base/securing-craft) guide where it concerns the server:

- Only `web/` is public; `config/`, `templates/`, `storage/`, `vendor/` and `.env` are outside the webroot, dotfiles are blocked.
- Code and dependencies belong to `root`. PHP can only write to `storage`, `web/cpresources`, `web/assets` and `.env`.
- Containers run as `www-data` (and `node` for Nuxt), never as root.
- Secrets come from Coolify's environment variables, database passwords are generated by Coolify.
- Images are rebuilt weekly and scanned with Trivy.

Because `config/` is read-only, production needs these settings in `config/general.php`:

```php
->devMode(App::env('CRAFT_ENVIRONMENT') === 'dev')
->allowAdminChanges(App::env('CRAFT_ENVIRONMENT') === 'dev')
```

Set the license key via the `CRAFT_LICENSE_KEY` environment variable (the content of `config/license.key`, from your local
install or craftcms.com → Licenses) unless `config/license.key` is committed. Without either, Craft tries to create
`config/license.key` on the first request and stops with `/app/config isn't writable by PHP. Please fix that.`
Site specific headers like `Content-Security-Policy` or `Permissions-Policy` belong in the project's
`.coolify/nginx/*.conf`, see [`examples/craft`](examples/craft/.coolify/nginx/custom.conf).
The remaining recommendations of the guide (Twig sandbox, `allowedFileExtensions`, escaping user input, …)
are project configuration.

## Configuration

Every setting lives in exactly one place:

| What | Where |
| --- | --- |
| PHP version | `ARG PHP_VERSION` at the top of `.coolify/Dockerfile` |
| Node version | `ARG NODE_VERSION` at the top of `.coolify/Dockerfile` |
| MySQL version | `image: mysql:8.4` in `docker-compose.yml` |
| nginx snippets | `.conf` files in `.coolify/nginx/`, included inside the `server` block |
| nginx site config | replace `/etc/nginx/site-opts.d/http.conf.template` completely (see `examples/craft-nuxt`) |
| Extra PHP extensions | `RUN install-php-extensions redis` in the project Dockerfile (while it runs as `root`) |
| PHP settings | serversideup env vars at runtime, e.g. `PHP_MEMORY_LIMIT`, `PHP_UPLOAD_MAX_FILE_SIZE` ([list](https://serversideup.net/open-source/docker-php/docs/reference/environment-variable-specification)) |

The examples let Coolify generate the database passwords (`${SERVICE_PASSWORD_MYSQL}`, `${SERVICE_PASSWORD_MYSQLROOT}`).
Craft gets its connection from the Environment Variables in Coolify, which reach every service:

```dotenv
CRAFT_DB_DRIVER=mysql
CRAFT_DB_SERVER=db
CRAFT_DB_PORT=3306
CRAFT_DB_DATABASE=db
CRAFT_DB_USER=db
CRAFT_DB_PASSWORD=$SERVICE_PASSWORD_MYSQL
```

MySQL only applies the generated passwords when the data volume is created: for an existing database, keep its
current password (set `SERVICE_PASSWORD_MYSQL` to it in Coolify) or change it in MySQL first.

> Upgrading MySQL to a newer major version on an existing volume usually works; downgrading does not. Take a backup first.

## Maintenance

- **Security updates**: the workflow rebuilds all images every Monday without cache. PHP patch releases
  (8.4.x) arrive the same way. Trigger "Run workflow" in the Actions tab to rebuild right away.
- **Vulnerabilities**: every build scans the images with [Trivy](https://trivy.dev) (fixable HIGH/CRITICAL findings).
  Results show up in the build log and under the repository's **Security > Code scanning** tab.
  On top of that, `scan.yml` checks the published images every day and rebuilds the affected PHP versions
  without cache as soon as a fix is available (Alpine packages via `apk upgrade`, PHP itself once serversideup ships it).
- **New PHP version**: add it to `php-versions.json` and push.
  Dropped versions keep their last tags on GHCR but are no longer updated.
- **Changes to the image** (new extension, …): edit `Dockerfile` and push to `main`.
- Projects pick up a new base image on their next deploy, as long as Docker pulls it. Pin a dated tag
  (`8.4-20261102`) if a project should only change on purpose.

## Local build

```sh
docker build --build-arg PHP_VERSION=8.4 -t craftcms-docker:8.4 .
```
